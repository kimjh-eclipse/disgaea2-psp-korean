# 렌더러 제약

이 프로젝트에서 가장 오래 붙잡은 부분입니다. **정적 검증이 전부 통과해도 화면은 깨질 수
있습니다.** 파일·바이트·인코딩이 모두 정상인데 폰트나 렌더러 쪽 조건이 어긋난 경우라,
반드시 실제로 대사를 띄워 봐야 드러납니다.

## 1. 대사는 모든 문자가 2바이트여야 한다

**증상** — 글자가 밀리고 엉뚱한 글자·쓰레기(`ww を ％`)·빈칸이 섞인다.

**원인** — 대사 렌더러가 **문자 경계를 무시하고 고정 바이트 오프셋으로 줄을 자른다.**
일본어는 거의 전부 2바이트라 어디서 잘라도 경계에 맞지만, 1바이트 ASCII가 섞이면 그
뒤부터 오프셋이 홀수가 되어 자르는 지점이 문자 중간에 떨어진다.

작업 버퍼에서 1바이트 밀린 사본을 직접 확인했습니다.

```
원문   [엄][마][～]  =  XX YY | f4 ce | 81 60
버퍼               =  YY f4 | ce | 81 60      ← 1바이트 밀림
결과   "엄마～" 가 "자[ce]～" 로 렌더
```

**대응** — 대사(talk, InProgramTxtDB)는 공백·구두점·숫자·영문까지 **전각**으로 넣습니다.

| ASCII | 전각 |
|---|---|
| 공백 | `　` (U+3000) |
| `. , ! ?` | `． ， ！ ？` |
| `~ : ; ( ) - /` | `～ ： ； （ ） － ／` |
| `0-9 A-Z a-z` | `０-９ Ａ-Ｚ ａ-ｚ` |

전각 영숫자 글리프는 원본 폰트에서 지워져 있어(`collect_fullwidth_alnum`) 62자를
복원해 넣었습니다.

> 반증된 값싼 대안: "문자열 길이만 짝수로 맞추기"(+32KB)는 실패했습니다. 같은 `……` 가
> 문자열 내 위치에 따라 깨지고 안 깨집니다. 조건이 문자열 단위가 아니라 더 안쪽에 있습니다.

## 2. 한글 코드의 후행바이트는 `0x80~0xFC` 만

**증상** — 글자 사이에 알파벳이 끼어든다. `해f도` `제R논` `필X요` `명g 년`

**원인** — 게임이 그 2바이트 코드의 글리프는 그리면서 **포인터를 1바이트만 전진**시켜,
후행바이트를 ASCII로 한 번 더 그린다.

| 후행바이트 | 표본 | 깨짐 |
|---|---:|---:|
| ≥ 0x80 | 27자 | 0 |
| < 0x80 | 13자 | 6 (`0x4D 0x52 0x58 0x63 0x66 0x67`) |

같은 선행바이트라도 `0xFB5D`(하)는 정상, `0xFB66`(해)는 깨집니다. 선행바이트가 아니라
후행바이트 값 문제입니다. `<0x80`이 전부 깨지는 것은 아니지만 **깨지는 것은 전부 `<0x80`**
이므로 그 범위를 통째로 피합니다.

```python
# krfont.n_to_code
return CODE_C1_BASE + n // TRAIL_N, TRAIL_BASE + n % TRAIL_N   # 0x80 + n%125
```

용량은 선행 `0xF0~0xFC` 13개 × 후행 125개 = **1,625자**. 실사용 1,218자로 여유가 있습니다.

## 3. talk 공용 버퍼 `0x318F8`

전량 전각화하면 talk 멤버가 커져 **공용 버퍼(203,000B)를 넘고 게임이 죽습니다.**

```
전각화 talk01 = 211,619B  >  203,000B  → 오버플로
```

EBOOT 9워드를 패치해 `0x36000`(221,184B)로 확장했습니다(`ori` 즉치값 `0x18F8` → `0x6000`).

```
0887A0BC  344718F8 -> 34476000      0892A640  344718F8 -> 34476000
08892A80  344518F8 -> 34456000      0892A680  344718F8 -> 34476000
08928F80  344718F8 -> 34476000      0892B57C  344718F8 -> 34476000
0892A35C  344718F8 -> 34476000      0892B5BC  344718F8 -> 34476000
0892A39C  344718F8 -> 34476000
```

버퍼를 잡는 코드가 이미 돌아간 뒤에 값을 바꾸면 크기 불일치가 남으므로, **완전 재부팅
시점부터** 적용해야 합니다. 그래서 EBOOT 자체를 교체하는 방식을 택했습니다.

> **SCRIPTPACK 총 크기와 ISO 슬롯에는 상한이 없습니다.** 한동안 "총 크기 상한"으로 오판했는데,
> 정상 팩 내용을 그대로 두고 뒤에 0만 붙여 3.48MB로 만들었더니 정상 부팅했습니다.
> 실패 사례들은 전부 전각화된 **내용**이 들어간 빌드였습니다. 크기는 무죄였습니다.
>
> 오판의 원인은 실험 설계입니다 — 총 크기를 단독으로 바꿔 본 적이 없었습니다.

## 4. 글리프가 비어 있는 ASCII는 채우면 안 된다

원본 폰트는 `$ & ' * : < > ? @ \ ^ ` q v z |` 의 글리프를 비워 두었습니다.
번역이 `?`를 1,984회 쓰는데 전부 빈칸으로 나와서, 빈 gid에 글리프를 구워 넣었습니다.

**그 결과 대사창에 `|` `'` 같은 쓰레기가 드러났습니다.** 해당 대사 바이트코드에 실제로
`[0b]z'[00][0b]X'[00]` 가 들어 있습니다.

원본이 글리프를 비워둔 것은 누락이 아니라 **바이트코드에 섞인 ASCII 값을 화면에서 숨기는
장치**였습니다. 글리프 베이크를 철회하고 전각(`？ ～ ： ＆ ＜ ＞ ’`)으로 대체했습니다.

## 5. 전각 기호는 크기를 다시 맞춰야 한다

원본 전각 글리프는 일본어 폰트용이라 잉크 높이가 12~13px인데, 우리 한글(돋움 12)은 11px
입니다. 그대로 쓰면 `？`와 숫자가 커 보입니다.

같은 서체로 다시 굽고, **세로 위치는 그린 뒤 잉크 박스를 재서 옮깁니다**
(`getbbox`로 예측하면 폰트마다 어긋나 `，`·`．`가 문장 중간에 뜹니다).

```
，．、。・   잉크 하단을 y=11 (베이스라인)
～－         잉크 중심을 y=6
그 외        한글 박스(y 1..11) 중앙
```

## 6. 이미지의 외곽선 비율

오프닝 나레이션은 512×512 4bpp 스위즐 아틀라스입니다. 1차 결과가 화면에서 뭉개졌는데,
아틀라스 자체는 선명했고 원인은 **외곽선 누락**이었습니다.

원본 팔레트는 두 구간으로 나뉩니다.

```
index 1~7    (0,0,8,a) 계열 = 검은 외곽선 알파 램프
index 8~15   회색~흰색      = 글자면
```

원본의 외곽선/글자면 픽셀 비율은 **1.45**입니다. 보라색 배경 위 흰 글자만으로는 대비가
무너져 축소 시 번져 보입니다. 수정본은 1.71로 원본과 동급입니다.

검증은 아틀라스를 언스위즐해 인덱스 1~7과 8~15의 픽셀 수 비를 원본과 비교하면 됩니다.

## 작업 방식에서 얻은 것

- **잘 되는 빌드를 실험으로 갈아치우지 말 것.** 전각화가 성공한 상태를 지우고 값싼 대안을
  시험해 결과가 더 나빠졌습니다. 실험은 다른 장면·사본으로 해야 합니다.
- **한 번에 하나만 바꿀 것.** 두 변수를 동시에 바꿔서 실패 원인을 몰라 시험을 두 번 더 했습니다.
- **세이브 스테이트로 확인하지 말 것.** 스테이트에는 이전 빌드의 텍스트가 RAM 이미지로
  들어 있어 폰트·코드표 변경이 반영되지 않습니다.
- **파일을 고쳤는데 화면이 그대로면, 그 파일이 실제로 쓰이는지부터 의심할 것.**
  유닛 이름 풀은 루트 `NAME.DAT`가 아니라 압축 아카이브 `START_VM_JP.LZS` 안의 사본이
  실제 사용처였습니다. 평문 검색으로는 보이지 않습니다.
